## CodeQL: verified reflection-taint result (2026-09-11)

Taint from `OpenSSLCipherConfigurationParser.parse(String expression)` (`.../openssl/ciphers/OpenSSLCipherConfigurationParser.java:724`) crosses the reflective `Class.forName("...OpenSSLLibrary").getMethod("findCiphers", String.class).invoke(null, elements[0])` and lands in `OpenSSLLibrary.findCiphers(String ciphers)` at `.../openssl/panama/OpenSSLLibrary.java:450`. ## CodeQL: whole-codebase sweep result (2026-09-12, broadened to 3 channels)

`qll/Sweep.ql` seeds sources at client HTTP input accessors (Coyote/Catalina `Request` getters: params/headers/URI/method/body) and reports every reflective boundary with a client-tainted argument across three channels — `method-invoke` (`Method.invoke`), `ctor-newinstance` (`Constructor.newInstance`/`Class.newInstance`, via `Reflection::NewInstance.getInferredConstructor()`), and `proxy-dispatch` (a call whose receiver locally flows from one of the 3 `Proxy.newProxyInstance` sites). Result: **method-invoke = 15 sites, all in `org.apache.jasper.runtime.JspRuntimeLibrary`** (`setProperty` L428/L438 + `createTypedArray` L575–671) — i.e. JSP `<jsp:setProperty>`; **ctor-newinstance = 0**; **proxy-dispatch = 0**. The only reflective constructor with args is `dbcp/dbcp2/ConnectionFactoryFactory.java:65` (config-driven, not client-tainted); the 3 proxy sites are `FilterValve:186`, `el/lang/ELSupport:726` (EL lambda → app content), `naming/factory/DataSourceLinkFactory:89` (config JNDI) — all out of scope. **Conclusion: no Tomcat-core reflection vuln surfaces from client HTTP input**; the sole crossing is the documented `<jsp:setProperty>` feature (target fixed by the app's compiled JSP, client controls only values → any exploitability is an app bug). Gotcha that cost a run: when rewriting `isDynamicProxyDispatch`, dropping the `isDynamicProxyCreation(np)` conjunct made `np` match *any* call flowing into another receiver (150+ false hits) — keep that conjunct. Re-run if you broaden sources or go inter-procedural on proxies.

## CodeQL API gotchas (this build)

This CodeQL build uses a NEWER signature-based taint API, not the classic one. Gotchas that cost real iterations:

- Config is `module C implements DataFlow::ConfigSig { predicate isSource(DataFlow::Node n){...} predicate isSink(...){...} predicate isAdditionalFlowStep(DataFlow::Node a, DataFlow::Node b){...} }`, then `module Flow = TaintTracking::Global<C>;` and query `Flow::flow(src, sink)`. There is no `TaintTracking::Configuration` class and no `isAdditionalTaintStep` (it's `isAdditionalFlowStep`).
- A `Parameter` is a `Variable`, **not** an `Expr` — you cannot write `n.asExpr() = param`. Match the node via `param.getAnAccess()` (the lib's own `frameworks/InputStream.qll` does exactly this). Same for sources.
- No chained comparisons: `0 <= i < n` is a syntax error; write `0 <= i and i < n`.
- `from` is a reserved keyword — do not name a predicate parameter `from`.
- Parameter count is `Method.getNumberOfParameters()` (not `getNumParameter()`); there is no `Type.isArray()`.

## CodeQL resolution limits / how to extend

`inferAccessedMethod()` only resolves targets that are statically knowable — literal `forName("...")` + literal-name `getMethod("name", ...)`. For dynamic targets (e.g. the modeler JMX proxy `BaseModelMBean.invoke/setAttribute`, or `JspServletWrapper.setProperty` where the method name and/or receiver come from request data), over-approximate instead: constrain candidate target methods by the receiver's static type + arity, emit an edge to param 0 of each candidate, and let taint fan out. Keep the precise path for literal cases; add a bounded over-approximation branch for dynamic ones so results stay inspectable rather than exploding.
